# Decisions

One line per resolution. BRIEF.md wins over PROMPT.md; PROMPT.md Layer 8 resolves open questions; "employee-level simple" breaks ties. Numbers verified by exact-decimal recomputation of every figure in the brief (0 failures).

## Math and Core

1. **Pricer takes plain values, not `Project`.** `Pricer.price(lines: [PriceLine], hours:, multiplier:, markup:, minimumJobCents:, billableHours:) -> Breakdown` with `PriceLine {bucket, rateCents, isOn, qty}` in `Sources/Core`; `Sources/Models` adds `Project.breakdown(billableHours:)`. Basis: BRIEF §5.4 "no SwiftData import" and Layer 1.2 outrank the sketch signature.
2. **`Bucket` enum lives in Core** (Foundation only, `Codable`, `CaseIterable`), used by Core and Models. Basis: Layer 5.
3. **Rounding pipeline (header always reconciles):** each bucket subtotal = exact `Decimal` rounded once; Cost = Σ subtotals; Price = max(minimum, round(Cost × (1 + markup) × multiplier)); Profit = Price − Cost; margin = Profit ÷ Price × 100, one decimal. Every §3.3 / Layer 7 figure is identical under this rule. Price is computed from the rounded Cost; with fractional hours this can differ by one cent from pricing the exact cost (6.5 hr: $2,070.44 vs $2,070.43), and the displayed Cost, Price and Profit always reconcile. Basis: BRIEF §5.2 round-once; §5.5 shows all seven figures together, so they must add up.
4. **Overhead is priced as Σ($/yr of on rows) × hours ÷ billable hours, rounded once** as the subtotal; per-row $/hr in tables is display-only rounding and never feeds the calculation. Basis: Layer 2 formula; BRIEF §5.2.
5. **The floor is applied after the multiplier and is never multiplied**: 1 hr × $20/hr at 2× = $54 → $750; cost $300 at 2× → $810. Basis: BRIEF §1 formula, §5.4 "floor applies after".
6. **"2× doubles the price" is tested on a cent-exact fixture** (10 hr × $100/hr → $1,350 / $2,700 / $4,050) plus a regression pinning the §3.3 project at 2× to $5,002.99 (exact 5002.992), which is not 2 × $2,501.50. Basis: BRIEF §5.2 round-once wins over the test's phrasing.
7. **EquipmentCalc computes the rate with ONE division** (the five components over their common denominator 2·life·annual, then rounded once); each displayed component is likewise one division over its own denominator. `Decimal` division truncates at 38 digits, so summing separately divided components put an exact half-cent tie one unit below the boundary and rounded it down (found by the Phase B breakers: 150 of 150 generated ties at the brief's defaults). Basis: BRIEF §5.2 round-once, half away from zero; OO's per-leaf rule is not ported. Bucket truck = 2372 either way.
8. **EquipmentCalc throws** for price ≤ 0, salvage < 0, salvage ≥ price, life ≤ 0, annual hours ≤ 0, or any negative fuel / repair factor / insurance / cost of money. `AVF = 1` when `N ≤ 1`. Basis: Layer 2 (superset of BRIEF §5.4) plus the divisions in §2.2.
9. **LaborCalc throws** for wage < 0, paid hours < 0, burden < 0, billable ≤ 0. Basis: same.
10. **Pricer never throws or traps** (it runs on every keystroke): billable hours ≤ 0 makes overhead contribute 0; negative or non-finite hours, qty, rates, markup and minimum are treated as 0; the multiplier is held to 1…3; all sums are carried in `Decimal`; margin is 0 when Price is 0. Settings refuses billable < 1. Basis: BRIEF §5.5 "recomputes on every keystroke"; BRIEF §1 (markup adds on top, the floor is a floor, 1×/2×/3× only); Layer 1.3 rules live in code.
11. **Decimal lift rule:** fractions and percents enter `Decimal` via `Decimal(string:)` or integer arithmetic, never `Decimal(Double)` or a float literal. Basis: Layer 1.2 "the math is exact"; usace-methodology §4.3 documents the Double corruption on this toolchain.
12. **Percent units:** any name ending in `Pct` is a whole percent (35); Core parameters `markup`, `burden`, `costOfMoney` are fractions (0.35). `@AppStorage` stores `billableHoursPerYear` and `minimumJobCents` as `Int`, the three percents as `Double`; the Models/Views layer divides by 100 exactly. `Project.markupPct` stores the whole percent. `Breakdown.marginPct` is a whole percent. Basis: Layer 3 names and defaults; Layer 7 signatures.
13. **Cost of money defaults to 0 and is a single global rate.** `EquipmentCalc` takes it as an explicit parameter (the 2372 test passes 0.07); the Equipment sheet reads Settings live, shows it read-only, and stores the value used in `calcInputs`. Changing Settings never recomputes stored rates. Basis: BRIEF §1 table, §6.3, Layer 8; §2.2 labels 7% "in this example".
14. **Pricer consumes stored cents only** (never recomputes from `calcInputs`): the brief's $124.39/hr is Σ rounded rates (exact Σ is 124.384) and §3.3 reproduces only from stored cents. Basis: BRIEF §5.3 `rateCents`, §3.4 snapshots.
15. **The §3.3 sequence is cumulative:** base $2,501.50 → Miguel off $2,170.48 → Miguel on + skid steer on $2,674.62 → same + 3 stumps $3,039.12 (skid steer still on). With the skid steer off, 3 stumps give $2,866.00. Basis: BRIEF §3.3 prose order.

## Data model

16. **Exactly the §5.3 fields.** No "current meter" field (§2.2's optional aside is maintenance tracking; `notes` can hold a reading). Basis: Layer 3 "verbatim", Layer 1.1.
17. **Snapshot at line creation; toggling never re-snapshots.** New project creates one `ProjectLine` per active `BucketItem` with name/unit/rate copied then; hourly lines on, quantity lines off with qty 1. Flipping a row off and on is side-effect-free so "flip things and watch" (§3.3) never silently changes a bid. Only Re-price refreshes copies. Basis: Layer 1.4 "editing a bucket row never changes an existing project"; BRIEF §3.3, §3.4.
18. **Re-price** = as if the project were created today, keeping toggles, quantities, hours and actuals: copy name/unit/rate from each line's item (archived included); leave nil-item lines untouched; refresh `markupPct` and `minimumJobCents` from Settings; append a line for every active item the project lacks (hourly on, quantity off qty 1). One button, no confirmation. Basis: BRIEF §3.4; §3.2 preset mechanism; Layer 8.
19. **Duplicate** copies everything verbatim (hours, multiplier, markup, minimum, client, notes, every line with its snapshot, toggle, qty and item link, archived or nil included), sets name = original + " copy" and date = today, and clears actual hours and every actual qty. It does not re-snapshot. Basis: BRIEF §3.2 "copies everything"; §3.5 actuals belong to the job that happened.
20. **New projects exclude archived items; duplicates keep them.** Basis: BRIEF §5.3 `isActive` comment, §3.2.
21. **Archived or deleted item behind a line:** the line stays, stays toggleable, prices from its snapshot, and shows a small "archived" / "row deleted" caption; Pricer never touches `item`. `ProjectLine.item` is optional and `BucketItem` declares the inverse `lines` relationship with a nullify rule, because without a declared inverse SwiftData leaves a deleted row's lines pointing at invalidated data and traps on access (found by test). Basis: BRIEF §5.3 comment; Layer 6 Phase B test.
22. **Delete vs archive:** Delete is enabled only when no `ProjectLine` references the item; otherwise the Active toggle (archive) is the path. Basis: BRIEF §5.5.
23. **`billableHoursPerYear` is not snapshotted on `Project`** (§5.3 verbatim); changing it re-prices the overhead subtotal of existing projects, and the Settings field says so. Labor and equipment rates are unaffected because their $/hr is stored. Basis: Layer 3 "verbatim"; BRIEF §1 "set once"; §2.0 "not a v1 concern".
24. **Markup and minimum are values in Settings; the rules are code.** No per-row or per-project override; the Project header shows the snapshot read-only. Basis: BRIEF §1 table, §5.5; Layer 1.3, Layer 8.
25. **Unit:** fixed and read-only for hourly buckets ("hr", "hr", "yr"); free text for Materials/Consumables, default "each", placeholder lists load / day / stump / application / roll / yard. No lookup editor. Basis: BRIEF §0 row kinds, §5.1.
26. **`source` exists on every row** (§5.3 verbatim) but the Form shows it only for Materials and Consumables. Basis: BRIEF §2.4, §5.3 comment.
27. **Bucket is set at creation and not editable**; to move a row, archive it and add a new one. Basis: BRIEF §0 row-kind table.
28. **`sortOrder`** = max in bucket + 1 on add; tables sort by `sortOrder` then name; no drag reorder. Project sections sort lines by their item's `sortOrder` then name; orphan lines last. Basis: BRIEF §5.3.
29. **`qty`** defaults to 1 at line creation for every line (unused on hourly lines); toggling never resets it; 0 is allowed and prices to 0. Basis: BRIEF §3.2.
30. **Hours, actual hours, qty, actual qty** are `Decimal`, non-negative, at most two decimal places, and bounded: hours ≤ 99,999.99, qty ≤ 999,999.99, any rate or price ≤ $9,999,999.99; empty or invalid entry = 0; Pricer uses the value exactly (6.5 hr → labor 124.39 × 6.5 = 808.535 → $808.54). With these bounds no figure can exceed 10^18 cents, so the saturation in 49 never fires in practice. Basis: BRIEF §5.3, §3.1; Phase B overflow probes.
31. **Variance is on cost at the project's snapshot rates:** hourly buckets = Σ on rates × actual hours (overhead ÷ billable); quantity buckets = Σ rate × (actual qty ?? qty) over on lines; variance = actual − estimate (positive = job cost more). Shown only once actual hours is entered; the Projects list shows signed dollars or "—". The Actuals table lists Estimate / Actual / Variance per bucket plus a total row with % of estimate. Basis: BRIEF §3.5 "we always miss hours by 20%".
32. **Bucket order everywhere is the enum order:** Labor, Equipment, Materials, Consumables, Overhead. Basis: BRIEF §5.3 verbatim, §0.

## Screens

33. **One window, three-column `NavigationSplitView`:** sidebar = "Buckets" section (5 rows) + "Projects"; a bucket shows Table → detail Form; Projects shows the list → Project screen. Settings is the standard macOS Settings scene (⌘,). Sheets and disclosure sections are not screens. Basis: BRIEF §5.5; Layer 1.7.
34. **No "Calculate…" sheet for Overhead.** An overhead row's only input is its $/yr, which is `rateCents`; the Form has one "$ per year" field with a read-only "= $X.XX/hr at N billable hours" caption, and `calcInputs` stays nil. Only Labor and Equipment rows get the sheet. Basis: BRIEF §2.3, §5.3 `calcInputs` comment (specific) over the §5.5 one-liner; a one-field sheet is a concept without content.
35. **Labor sheet:** wage $/hr, paid hours (default 2,080), burden % (default from Settings, editable per row), billable hours read-only from Settings; Save stores the rounded rate and `calcInputs {wageCents, paidHours, burdenPct}`. Reopening shows saved inputs. Rates may also be typed directly. Basis: BRIEF §2.1, §5.3.
36. **Equipment sheet:** the 7 inputs (defaults: annual hours = Settings billable hours, life 8,000, repair factor 0.80) with the §2.2 ranges as static help text, cost of money read-only from Settings; Save stores the rate and `calcInputs` (7 inputs + cost of money % used). No type picker, no defaults table. Basis: BRIEF §2.2; Layer 1.1 no lookup editors.
37. **Buckets Table "Rate" column** shows the stored figure as currency; overhead cells add the derived $/hr as secondary text; the "Unit" column shows the unit string; "Active" is the `isActive` toggle, and archived rows stay listed in secondary color so they can be restored. Basis: BRIEF §2.3, §5.3, §5.5.
38. **Project header top row** edits name, client and date; notes is a field below the sections; a new project is named "New project" dated today. Basis: BRIEF §5.3 fields.
39. **Price uses `.font(.largeTitle)`**; every text is a semantic style; no numeric point sizes. Basis: Layer 1.7.
40. **Multiplier** is a segmented Picker: "1× Normal · 2× After-hours · 3× Emergency". Basis: BRIEF §1.
41. **Copy price** puts `<project name> — $2,501.50` on the pasteboard, nothing else. **Copy breakdown** puts one line each: name, date, hours, multiplier, the five subtotals, Cost, Markup %, Price, Profit (margin %). Never a row name, rate, or the word "sub". Basis: BRIEF §2.5, §5.5.
42. **⌘N is context-sensitive** (new row in a bucket, new project in Projects); ⌘D duplicates; Delete asks for confirmation. Basis: BRIEF §5.5.
43. **Export/Import JSON:** one document `{formatVersion, exportedAt, settings, items[], projects[{…, lines[{itemIndex?, …}]}]}`; lines reference items by array index so no id field is added to the models; `calcInputs` is embedded as JSON. Import replaces the whole store after one "Replace all data?" alert and applies the settings. That alert is not an "import prompt" (those were OO's launch-time nags). Basis: Layer 4 "full round-trip"; Layer 6 Phase D; BRIEF §5.1.
44. **Store:** no App Sandbox, no hardened runtime, ad-hoc signing; `ModelConfiguration(url:)` pinned to `~/Library/Application Support/Buckets/Buckets.store` (SwiftData adds `-wal` / `-shm` sidecars; deleting the store means all three). Basis: Layer 3 path, Layer 5 "sign to run locally".
45. **Swift 6 language mode**, strict concurrency complete; views and the app entry are `@MainActor`. Falls back to Swift 5 mode only if `@Model` isolation blocks Phase C (would be logged here). Basis: Layer 5.
46. **Deployment target macOS 15.0**; no macOS 26-only API; verified on macOS 26.4 with Xcode 26.6. Basis: BRIEF §5.2.

## Build environment

47. **DerivedData lives in `~/Library/Developer/Xcode/DerivedData/Buckets-cli`** (override `BUCKETS_DERIVED_DATA`): `~/Desktop` is iCloud-synced and the file provider stamps Finder attributes onto bundles, which makes codesign fail with "detritus not allowed". `build/Buckets.app` is a stripped copy.
48. **Screenshots** launch the built binary with `BUCKETS_APPEARANCE=light|dark` (read in `applicationWillFinishLaunching`, never in `App.init` where `NSApp` is nil) and an optional `BUCKETS_SCREEN` to open on a given screen; `Scripts/window-id.swift` resolves the window; `screencapture -l` captures it.

## Hardening (Phase B adversarial pass)

49. **Money.cents saturates and neutralises:** a NaN or infinite `Decimal` becomes 0 cents; an amount beyond `Int` becomes `Int.max` / `Int.min` instead of wrapping modulo 2⁶⁴ (which priced a $30-quadrillion job at the $750 floor). `Money.format` goes through the unsigned magnitude so `Int.min` formats instead of trapping. Pricer clamps negative rates, markup and minimum to 0 and holds the multiplier to 1…3 (see 10). Unreachable with the bounds in 30; found by the Phase B breakers with 15-digit hours and `Int.max` rates.
50. **Core API shape vs the §5.4 sketch:** `Pricer`, `LaborCalc`, `EquipmentCalc` are case-less enums with static functions; Layer 7's `LaborCalc(wage:…) == 5408` reads as `LaborCalc.rateCents(wage:paidHours:burden:billable:)` and `EquipmentCalc(…) == 2372` as `EquipmentCalc.rateCents(price:salvage:lifeHours:annualHours:fuelOilPerHour:repairFactor:insurancePerYear:costOfMoney:)` with the same labels. `Breakdown` adds `subscript(bucket:)` and `.zero`; `Bucket` adds `title`, `rowKind`, `fixedUnit`, `isAnnual`; `PriceLine.init` defaults `isOn` from the row kind (hourly on, quantity off, §3.2).
51. **Decimal(string:) contract for the Views layer** (pinned by `DecimalParsingContractTests`): it stops silently at the first unusable character ("2,500.00" → 2), returns 0 for whitespace-only or a lone "-", nil for "" and "abc", and no locale understands grouping. The shared fields therefore strip "$" and "," before parsing, reject anything that is not a plain non-negative number with at most two decimals, and apply the bounds in 30.
52. **Screenshot fixture and render hooks:** `BUCKETS_FIXTURE_STORE` moves the `--fixture` store out of `build/fixture/` when iCloud holds that Desktop folder (SQLite's directory fsync then blocks in `open(2)`, the same file-provider problem as 47); `--render` draws the main window from its frame view so the toolbar is in the capture, and `BUCKETS_WINDOW_SIZE=WxH` enlarges the window first so the Project screen renders past the fold. `BUCKETS_SCREEN=project` opens the oldest project by date (the fixture's "Oak removal", the §3.3 example). Basis: 47, 48; Layer 6 Phase C screenshot checks.
53. **Settings window offscreen render:** on macOS 26 the `Settings` scene hosts its content in SwiftUI's own window container, whose layer tree has no drawable contents while the app is in the background (the main window's columns are classic `NSHostingView`s and render fine). `BUCKETS_SCREEN=settings --render` therefore draws the same `SettingsScreen` through an `NSHostingView` in a stand-in titled window of the same size and appearance (`AppDelegate.settingsSnapshot`), written as `settings.png`. Screenshot-only; the real Settings window is unchanged. Basis: 48, 52; Layer 6 Phase C screenshot checks.
54. **Phase D runs as an XCUITest target (`BucketsUITests`)**, a third target beyond the two the prompt names: it is the only permission-free way on this Mac to drive the real UI from the CLI (Accessibility is not granted to the agent's host app, so AppleScript UI scripting cannot be used). The test launches the app against a temp store via `BUCKETS_STORE`, types the 25 rows in through the Buckets screen, prices the §3.3 project and checks $2,501.50 → $2,170.48 → $2,674.62 → $3,039.12 and the actuals variance. Rates are typed directly (DECISIONS 35 allows it); the calculator sheets are covered by `BucketsScreenTests`. Export/Import through the save/open panels is not driven by the test (panel automation is brittle); the round trip is covered by `ModelsTests`.
55. **"Add or Update Rows…" (merge) beside Import (replace):** adds a file's rows to the buckets and updates rows with the same bucket + name (case- and whitespace-insensitive) from the file (rate, unit, source, notes, calculator inputs); rows the file does not name are untouched; the file's projects and settings are ignored; nothing is deleted. Requested by Alexander 2026-09-15 so a researched starter catalog can join rows he had already typed. "Duplicate Row" on the Buckets screen copies a row to add another unit; unit and serial numbers go in the row's Notes (the Equipment form prompts for them) rather than a new model field.
56. **App icon:** a tree growing out of a bucket, drawn by `Scripts/make-icon.swift` into `Sources/Resources/Assets.xcassets`. The colors in that script are icon artwork; the app UI still uses system semantic colors only.
57. **Category and Link on every row** (two optional strings added to `BucketItem`, 2026-09-15 at Alexander's request): Category groups the tables (sortable column, default order for Materials and Consumables) and the project's bucket sections; Link is the product or supplier page, opened from the Form. Tables are searchable across name, category, unit, source and notes. Both fields ride along in Export/Import and the merge. SwiftData migrates existing stores automatically (new optional attributes).
59. **`BUCKETS_EXPORT_FILE` launch hook:** the app writes a full Export JSON to the named path at startup; pairs with 58 so backups and restores can be scripted without the save panel.

## Owner-directed v1.1 (2026-09-16; supersedes the brief's 3-model / 4-screen limits and its v1.1 deferral)

60. **Subcontractors are the sixth bucket, each sub a record with its own services.** `Subcontractor` (name, contact, phone, email, notes, active) owns `BucketItem`s in the Subcontractors bucket; a service prices exactly like a consumable (flat, all-in, per unit) and stays out of customer-facing output. Delete a sub only when none of its services is on a project; otherwise archive (which archives its services). The Subcontractors screen manages subs and their service lists in one place.
61. **Packages** are projects flagged `isTemplate`, listed under Projects → Packages. "Use Package" copies one into a new project at today's date and today's rates (Re-price runs on the copy). "Save as Package" does the reverse. Packages never show actuals.
62. **Loadouts** (`Loadout`: name, notes, members) are crew formations of labor and equipment rows, listed under Projects → Loadouts. The project header's Crew menu applies one: labor and equipment lines are turned on when their row is a member, off otherwise, missing active members are appended on; the project remembers `crewName` until a labor or equipment toggle is changed by hand. Loadouts add no pricing.
63. **Merge file rules extended:** a file can archive a row it names (never un-archives), carries subcontractors (matched by name) and loadouts (matched by name, members by the file's item positions); export/import round-trip all of it, and older files without the new keys still read.
64. **Default vault edition:** labor and equipment empty, overhead a $0 checklist, materials and consumables expanded for professional tree work, no subs, packages or loadouts; the company edition keeps Sacred Tree's rows.
65. **Company screen** (sidebar → Company; 2026-09-16, Alexander): one `Company` row (legal name, DBA, owner, address, phone, email, website, EIN, licenses & certifications text, three insurance policies with carrier / number / expiration, notes) in the content column, and the company's documents in the detail column. Expirations show red when past and orange within 30 days. Export/Import carry the profile and the document records; the Documents folder must be copied alongside the store to move the files themselves.
66. **Equipment identification:** `unitCode`, `make`, `model`, `year`, `serial` on every row (shown only for Equipment). The unit code is the crew's short name ("SAW-01", "TRK-02"); it is suggested from the row's category (Chainsaws → SAW, Trucks → TRK, Trailers → TRL, Machines → MCH, Pole saws → PSW, else the first letters) as the next free number, shown before the name in the Equipment table, project sections and loadouts, and searchable. Duplicate Row copies make/model/year, assigns the next code and leaves the serial blank, so a second identical saw is one click plus its serial.

## Buckets Pro v0.2.0 — field-ready estimating baseline (2026-09-24, issue #3, Mr. Anderson)

72. **Row trust and review.** Seven optional fields on every `BucketItem`: `evidence`, `checkedAt`, `reviewDueAt`, `confidenceRaw` (`Confidence`: missing · estimated · ownerConfirmed · verified; nil reads as missing, so a v1.1 store and a never-reviewed row look alike), `approvedBy`, `assumption`, and `needsOwnerConfirmation` (default false). A row is **unresolved** in exactly one group, by precedence: missing → owner confirmation needed → review overdue (`reviewDueAt` in the past) → estimated; verified and owner-confirmed rows with nothing outstanding are resolved, so the group counts add up. **Verified needs evidence (source, evidence note or link) and a checked date:** `markVerified` refuses otherwise and the Form offers Verified only once both exist. Owner confirmed clears the confirmation flag and records a checked date when none exists; "Today" on the checked date sets the review due a year out unless one is set. The Buckets table gains a Review column and a Show menu (all · unresolved · one group; flat list while filtering); the row Form gains a Review section; a subcontractor service gets the same fields in a sheet, since it has no Form of its own. A project line that is **on** and whose current row is unresolved shows a caption, and the header counts them ("3 enabled rows use unresolved catalog inputs — price unchanged"); pricing is untouched, the line still prices from its snapshot (17). Deleted and archived rows keep their own captions (21). Basis: roadmap Release 1 §2; issue #3 §1, §3, §4.
73. **Setup & readiness** is the first section of the Company screen: the required inputs (company name; service area, a new `Company.serviceArea`; billable hours ≥ 1; target margin > 0; minimum job > 0; at least one active labor, equipment and overhead row), completion per bucket over active rows with the last verified date, and the four unresolved counts, each with a Show button that opens the Buckets screen filtered to that group (`AppState.reviewFilter`, window-level). Status is **Not ready** while any input is unresolved, **Needs review** while any active row is, else **Ready** — never Ready with an unresolved input. `Readiness` is a plain struct in Models; `CompanyReadinessSection` renders it. Archived rows count nowhere (they are hidden from new projects; old projects get the line caption). Basis: roadmap Release 1 §1; issue #3 §2.
74. **Transfer format 2.** Export writes `formatVersion: 2` with the review fields (`confidence` omitted when missing, `needsOwnerConfirmation` only when true) and `company.serviceArea`; import and merge read formats 1 to 2 (`readableFormatVersions`) and refuse anything newer, naming the range. Merge applies the review fields a file carries and leaves the rest; a file cannot make a row verified without evidence and a checked date (it lands as estimated), so a hand-edited catalog cannot vouch for a row the app would not. A v1.1 app refuses a format-2 file rather than silently dropping the fields. The store migrates in place (new optional attributes, as 57), pinned by `StoreMigrationTests`: the v1.1 models are declared in the test target as a `VersionedSchema` (`BucketsSchemaV11`, nested classes with the app's entity names), the test writes the §3.3 rows and two projects with that schema, then opens the file with the app's schema and checks every row, project and price. No store file is committed (AGENTS.md forbids raw SwiftData stores in Git, synthetic or not). Basis: issue #3 §5.
75. **Versioning restarts at 0.2.0 for Buckets Pro** (issue #3 §6): `MARKETING_VERSION 0.2.0`, build 2, after v1.1 (build 1). The marketing number goes down; the build number, which is what macOS compares, goes up. The image is `Dist/Buckets-0.2.0.dmg`.
76. **A catalog file carries no company settings** (2026-09-24, Mr. Anderson, resolving audit §6(a)): `Scripts/catalog/data/Buckets-default-catalog.json` and the starter catalog ship rows only, and `build_catalog.py` no longer emits `settings`. `TransferDocument.settings` is optional: Import applies a file's settings when it has them (a company export) and keeps the company's when it does not (a catalog); merge ignored them already (55); exports always write them. The old default carried markup 35 %, burden 30 %, minimum $750 and 1,500 billable hours — one company's numbers, which every new company would have inherited. Pinned by `DefaultCatalogTests`.

92. **Sales allowance and commission in the price rule** (2026-09-30, Mr. Anderson: track the salesperson's commission as a bonus and price commissions accurately; plan 13, decisions 1, 2, 4 and 5). `PriceRule.targetMargin(M, allowance: A, burden: B)` prices `Price = max(min, round(Cost × 10000 × k ÷ (10000 − share)))` with `share = min(100·M + A·(100 + B), 9500)`: one division, rounded once (7, 70), the floor after the multiplier (5). M is the target margin *after* commission; A is the company's sales allowance, the share of every price set aside for commission, so a package has one price whoever sells it (a per-salesperson denominator was rejected: it would quote a customer differently by who answered the phone); B is the employer payroll tax on each commission dollar, default 7.65 (FICA; not the crew's 30% labor burden, which is mostly workers' comp). Both are Company → Pricing defaults (`salesAllowancePct`, default 0; `commissionBurdenPct`, default 7.65) and each is held to 0…100; the Company fields refuse any margin, allowance or tax that makes `M + A(1 + B/100)` pass 95. With A = 0 the code runs 70's expression `Cost × 100 × k ÷ (100 − M)` unchanged, so every figure pinned before this entry is identical (`PricerCommissionTests` loops over the §3.3 and margin fixtures), and two rules that price identically are equal (with A = 0, B has nothing to act on). The commission is `round(Base × C ÷ 100)` and its tax `round(Base × C × B ÷ 10000)`, each rounded once from cents; Base is `CommissionTerms.baseCents ?? price` (the sold price once slice 3 adds it; the price until then), one base for the header and any later report; `profitAfterCommission = Base − Cost − Commission − CommissionTax` by integer subtraction, so the header reconciles (3), and `marginAfterCommissionPct = ProfitAfter ÷ Base × 100`. `Breakdown` gains those four fields; without commission terms the last two equal Profit and Margin. The project snapshots A and B beside the target margin (`Project.salesAllowancePct`, `commissionBurdenPct`) in new projects, Use Package and Re-price; nil reads as 0, so a project from before 0.2.4 prices as it did and pays no payroll tax on a commission until it is re-priced. Legacy markup projects (`targetMarginPct == nil`) ignore A and still pay a named salesperson's commission. The markup equivalent is `share ÷ (10000 − share) × 100` (50/7/7.65 → 135.49%); `markupPct` and the export's settings `markupPct` carry it. The header: with A = 0 and no commission it is exactly as before; otherwise the margin reads "50% · 7% allowance", a Commission figure ("$366.04 · 7%", captioned "+ $28.00 payroll tax") appears only when a commission is paid, and Profit is the profit after commission, captioned "50.0% after commission · $3,008.65 before", "57.5% margin · no commission", "42.5% after commission · below 50% target" (`.orange`; the one-decimal margin under the target) or "loses $59.27 after commission" (`.orange`). Copy price is unchanged. Copy breakdown adds after Price "Sales allowance: 7% (+7.65% payroll tax)" when A > 0, "Commission: $366.04 (7%)" and "Commission payroll tax: $28.00" when a commission is paid, and after Profit "Profit after commission: $2,614.61 (50.0% margin)" whenever the header shows commission; it never carries a person's name (41). Packages snapshot A and B as they snapshot the margin, so Company shows "N packages priced under an older allowance" with **Re-price packages** whenever a margin package's `A·(100 + B)` differs from today's (never while A is 0 on both sides, so installing 0.2.4 shows nothing); the action re-prices every package, no ordinary project, and reports how many were stale.
